# Orders API on PostgreSQL

A service that takes orders and moves them through payment and shipping, stored in PostgreSQL so
the data survives a restart.

## Storage

- `DATABASE_URL` is a PostgreSQL connection URL, for example
  `postgres://user:password@localhost:5432/orders?sslmode=disable`. The database exists but may be
  empty: the service creates its tables when they don't exist yet.
- Every order must be stored in that database: after the service is stopped and started again
  with the same `DATABASE_URL`, everything is still there.

## Order

| Field        | Type   | Rules                                                              |
|--------------|--------|--------------------------------------------------------------------|
| `id`         | string | Generated by the server, unique                                    |
| `customer`   | string | Required, not blank                                                |
| `items`      | array  | Required; at least one item (see below)                            |
| `total`      | number | Computed by the server: the sum of `quantity × unit_price` over the items, rounded to 2 decimal places |
| `status`     | string | `pending`, `paid`, `shipped`, or `cancelled`; `pending` when created |
| `created_at` | string | RFC 3339 timestamp, set by the server when created                 |
| `updated_at` | string | RFC 3339 timestamp, set by the server on every change              |

Each item is an object:

| Field        | Type    | Rules                     |
|--------------|---------|---------------------------|
| `sku`        | string  | Required, not blank       |
| `quantity`   | integer | Required; 1 or more       |
| `unit_price` | number  | Required; 0 or more       |

## Endpoints

| Method and path             | Success                        | Errors              |
|-----------------------------|--------------------------------|---------------------|
| `POST /orders`              | `201` with the new order       | `400`, `422`        |
| `GET /orders`               | `200` with a page of orders    | `400`               |
| `GET /orders/{id}`          | `200` with the order           | `404`               |
| `POST /orders/{id}/pay`     | `200` with the order, now `paid` | `404`, `409`      |
| `POST /orders/{id}/ship`    | `200` with the order, now `shipped` | `404`, `409`   |
| `POST /orders/{id}/cancel`  | `200` with the order, now `cancelled` | `404`, `409` |
| `GET /health`               | `200`                          |                     |

- `POST /orders` takes `customer` and `items`. The client can't set `id`, `total`, `status`, or
  the timestamps.
- `GET /orders` accepts an optional `status` query parameter that lists only orders with that
  status; an unknown status is a `400`.
- Status changes: only a `pending` order can be paid, only a `paid` order can be shipped, and
  only a `pending` or `paid` order can be cancelled. Any other change is a `409`, and the order is
  left as it was.

## Conventions

- Request and response bodies are JSON.
- Errors respond with a JSON body `{"error": "<message>"}` and the status code:
  `400` for a body that isn't valid JSON or an invalid query parameter, `404` when no order has
  the ID, `409` for a status change that isn't allowed, `422` when the data breaks a rule above.
- Lists: `GET /orders?limit=<n>&offset=<n>` responds with
  `{"items": [...], "total": <number of matching orders>, "limit": <limit used>, "offset": <offset used>}`,
  oldest first. `limit` defaults to 20 and larger values than 100 are treated as 100; `offset`
  defaults to 0. A negative or non-numeric `limit` or `offset` is a `400`.
