# GoForge Roadmap

GoForge generates the infrastructure of a Go backend (the server, storage, tests, and tooling) so
developers and AI coding agents can spend their effort on the business logic. This roadmap plans the
next three phases. Each phase ships as a release.

## Principles

- **One tool for humans and agents.** The same commands serve both: readable output in a terminal,
  structured JSON for programs. No separate "agent mode" that can drift from the real tool.
- **Depth over breadth.** A smaller set of features that are generated, tested, and verified end to
  end beats many shallow ones. New protocols and integrations wait until the core is solid.
- **Claims are measured.** Statements such as "agents use fewer tokens with GoForge" are backed by a
  published, reproducible benchmark.
- **Every change is all or nothing.** Commands plan every edit before writing and roll back on
  failure, as they do today.

## Done: v0.1.0

Server generation; `goforge add resource` (CRUD with validation, pagination, PATCH, and tests);
`goforge add db` for PostgreSQL, MySQL/MariaDB, SQLite, and MongoDB; CI, Docker, and lint for
generated projects; automated, reproducible releases.

## Phase 4 (v0.2.0): Discoverable and agent-ready

**Status:** released in v0.2.0; the benchmark followed in v0.2.1. The awesome-go listing remains.

**Goal:** an agent or developer looking for a way to build a Go backend finds GoForge, can tell
within seconds that it fits, and can drive it without a human at the keyboard.

### Deliverables

1. **Discoverability**
   - README that leads with what GoForge does and when to use it, with a copy-paste example
   - "Using GoForge from an AI agent" section and an [`llms.txt`](llms.txt) for language models
   - GitHub description, topics, and social preview image that match what people search for
   - An honest comparison with the alternatives (go-blueprint, `gonew`, Goa): when to choose each
2. **Visible errors in generated projects**
   - Unexpected 500 errors are logged with their cause and request ID. Today the cause is discarded,
     which leaves the developer or agent guessing.
   - Error responses include the request ID; with `APP_ENV=development` they also include the cause
   - A request-scoped logger, so every log line from a request carries its request ID
   - (Startup already reports every invalid setting at once.)
3. **One result, two renderings**
   - Every command returns a structured result: files created and changed, notes, next steps
   - `--json` prints it as JSON, and errors carry stable codes (such as `marker_missing`)
   - Without a terminal, `generate` uses flag values and defaults instead of stopping
4. **`goforge inspect`**: describes a project (options, resources and fields, database, routes, and
   extension points) as text or JSON, so an agent can understand it without reading the code
5. **`goforge check`**: runs gofmt, vet, lint, and tests, and reports failures as structured results
   (file, line, test, message) instead of raw output
6. **`AGENTS.md` in generated projects**: how the project is laid out, which `goforge` commands to
   use, and how to verify changes
7. **Benchmark, first run**: about five backend tasks (such as "a products API on PostgreSQL with
   validation and tests"), each done by an agent from scratch and with GoForge, measuring tokens,
   cost, time to passing tests, correction cycles, and test pass rate. The harness lives in the repo
   so anyone can reproduce it.
8. **Listings**: submit GoForge to awesome-go. It meets their criteria (a year of history, a
   `vX.Y.Z` release, docs on pkg.go.dev, about 88% test coverage, published on Coveralls); only the
   submission remains. (Go Report Card, once planned here, has shut down.)

### Done when

- Every command supports `--json`, and none can block waiting for input
- A generated project logs every 500 with its cause
- `inspect` and `check` work on every option combination the end-to-end tests generate
- The benchmark has a baseline and a first comparison, and its harness is in the repo

### Order

The benchmark comes last, after every other Phase 4 item, so it measures the finished phase.

## Phase 5 (v0.3.0): In the agent ecosystem, with an API contract

**Goal:** GoForge is available where agents look for tools, and generated APIs describe themselves.

### Deliverables

1. **Agent skill**: teaches agents when and how to use GoForge, published where Claude Code and
   Codex users install skills and plugins
2. **`goforge mcp`**: a Model Context Protocol server exposing `generate`, `add`, `inspect`, and
   `check`, built on the Phase 4 JSON results and listed in the MCP registry
3. **OpenAPI from resources**: an OpenAPI 3.1 document generated from `.goforge.json` (paths,
   schemas, pagination, errors, required fields), served at `/openapi.json` with an optional `/docs`
   page, regenerated by `goforge add`, and checked by a generated test so it can't go stale
4. **Homebrew tap**: `brew install frank5ive/tap/goforge`, published by the release workflow
5. **Benchmark, published**: rerun with the skill and MCP server; publish the method and results
6. **Launch**: a "Show HN", r/golang, and a blog post built around the benchmark results

### Done when

- An agent with only the skill or the MCP server can build a working, tested API with GoForge
- Every generated API serves a valid OpenAPI document that matches its routes
- `brew install` works for each release
- Benchmark results are published with instructions to reproduce them

### Decisions needed

- **Homebrew:** create a public `homebrew-tap` repository and a token the release workflow can use
- **Docs page:** whether `/docs` loads a viewer from a CDN or the project embeds one

## Phase 6 (v0.4.0): Production features

**Goal:** a generated API can go to production without hand-written security or monitoring code.

### Deliverables

1. **`goforge add auth`**: authentication, and `goforge add resource --auth` to protect a
   resource's routes. Scope to be decided (see below).
2. **Richer resources**
   - Filtering and sorting on list endpoints, e.g. `?sort=-created_at&in_stock=true`
   - Unique fields (v0.2.1 added ranges, `email`, and `ref` fields)
3. **`goforge add observability`**: OpenTelemetry tracing (requests and database calls) and
   Prometheus metrics, off by default
4. **`goforge doctor`**: checks a project's markers and `.goforge.json`, and explains how to fix
   anything a `goforge add` command can no longer update

### Done when

- Each feature works with the in-memory store and all four databases, and is covered by the
  end-to-end tests
- Auth passes a security review of password storage, token handling, and the generated tests

### Decisions needed

- **Auth scope:**
  - **A. User accounts:** a users table, register and login endpoints, bcrypt password hashing, and
    short-lived JWT access tokens with refresh tokens
  - **B. Token verification only:** the API checks tokens issued by an identity provider (Auth0,
    Clerk, Keycloak, and similar) and doesn't manage users
  - A can include B's mode later. Either uses a maintained JWT library rather than hand-written
    cryptography.

## Later

Considered after Phase 6, and driven by benchmark results and user demand:

- **gRPC** as a second protocol on the same service layer, which proves the shared core
- WebSockets and event-driven messaging
- Kubernetes manifests
- GraphQL (lowest priority)
